# `/sdd-plan`

## 职责

接受 `draft` 或 `planned`，从 `draft.md` 生成含技术目标的批准前草稿；不修改正式代码、不批准、不创建阶段记录。

```text
/sdd-plan <change-id>
```

## 读取

### 固定读取

- 当前 change 的 `draft.md`，以及当前 change 中真实存在的既有 `plan/spec.md`、`plan/design.md` 和 `plan/tasks.md`
- [`../rules/change-documents.md`](../rules/change-documents.md)、[`../rules/specifications.md`](../rules/specifications.md)

### 条件读取

每次只处理一个明确的事实缺口；同一事实被前一层唯一确认后，不得进入后一层。不同事实分别证明，不得用一个缺口授权批量读取：

1. draft 已指向现有能力时，只读取该能力的确切当前规格；不得枚举或通读其他规格。
2. 仅按 draft 明确涉及的产物类型与调用范围，读取 `AGENTS.md` 路由的确切实现规则；未涉及核心命名模板调用、values、Schema 或用户文档时，不读取对应规则。
3. draft 已给出唯一目标路径时，默认只检查该确切路径和 draft 已给出的确切标识符是否存在，不读取定义正文。只有 draft 明确修改现有行为，且当前规格与适用规则仍无法确定修改落点时，才读取命中声明的完整定义；读取只确认实现结构，不得形成契约。不得因此读取调用方、相邻文件或同目录其他能力。
4. draft 未给出唯一目标路径，且当前规格与适用规则仍无法解析时，才列出候选父目录的直接文件名；路径一旦唯一即停止，不读取未选候选文件。
5. draft 明确依赖命名能力，而当前规格和适用规则未声明其确切名称、入参或最小返回边界时，才读取该依赖的确切当前规格；仍缺少同一个接口事实或与正式声明冲突时，才读取正式代码中的对应 `define` 片段，不读取整份依赖文件或实际调用链。
6. 只有规格、规则和依赖声明仍无法确定直接依赖的类型或错误边界，且该事实会改变当前契约时，才读取 plan 已确定调用位置的确切调用片段；不得读取完整调用方或沿调用关系继续追踪。
7. 只有仍缺少影响契约的版本特定 API 事实时，才以 [`../references/README.md`](../references/README.md) 路由到精确的本地参考片段；本地片段仍不足时才查询精确的外部官方资源。
8. 技术目标唯一后，只列出 `openspec/changes/` 下除 `archive/` 与当前 change 外的直接活动 change 目录；存在其他活动 change 时，仅读取其 draft frontmatter 和 `plan/spec.md` 的 `## 技术目标`，并在目标不重叠时立即停止。

### 禁止读取

- 不读取其他 change 的正文、完整 plan、records 或 verification，不读取任何归档正文。
- 不为已经确定的字段顺序、类型、调用契约或实现规则补充代码与参考资料佐证。
- 不因目标文件已有实现或与 draft 不一致而制造新需求、设计选择或待确认问题；实现偏差只记录为实施差距。待确认问题必须直接来自 draft 内部无法并存的意图，或适用规范无法唯一决定且确实影响契约的选择。

## 输出

- 先按变更文档规则写回本轮确认的意图；`planned` 的 draft 有变化时先退回 `draft`。已批准时停止并要求 `/sdd-revise`。
- 解析 `## 技术目标` 并写入 `plan/spec.md`。用户写明的目标优先，但仍须按适用工程规则校验；目标不唯一、非法或冲突不阻止生成草稿，但必须记录候选项和待确认问题。
- 只从本轮按上述边界实际读取的目标 API 或产物结构、当前规格与适用规则补齐必要工程细节；条件上下文未触发时不得引用。正式代码只用于记录现状与实施差距，不得扩张用户需求。
- `plan/spec.md`：记录技术目标、可观察行为、失败边界与 Scenario 草稿。
- `plan/design.md`：记录适用规则在当前目标上的具体落实，包括重要技术决策、直接依赖、调用位置、传入上下文、处理顺序、类型与隔离边界；存在这些内容时必须创建，不需要时删除旧文件。
- `plan/tasks.md`：使用 Markdown 任务列表，只列 `/sdd-apply` 的实施顺序，不承载新的需求、设计约束或验证步骤；完成状态由 `/sdd-apply` 更新。
- 写入后逐条复核本轮读取的规范性规则；不得用“遵循项目规则”代替具体落实。存在规则遗漏或冲突，或技术目标、用户意图、设计选择、验收仍待解决时保持 `draft`；全部落实且无待确认项后才进入 `planned`。
- 会话中只报告技术目标、草稿产物和待确认问题。

再次执行时覆盖刷新 AI 草稿，不叠加历史说明。需求派生遵循变更文档规则。

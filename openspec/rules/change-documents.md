# 变更文档规则

## draft.md 保护规则

1. `draft.md` 是用户唯一输入入口；用户只维护表达意图的正文，frontmatter、`plan/` 和 `records/` 由 AI 维护。
2. AI 可以生成草稿，但不得覆盖、弱化或静默改写用户已确认的意图。
3. 用户明确写出或在会话中确认的内容优先于 AI 推断。
4. AI 推断内容必须标记 `[AI 推断]`；这是 draft 中唯一的特殊标记，不得伪装成用户需求或明确约束。
5. 未经用户确认，`[AI 推断]` 条目不得派生 MUST 或 SHALL。
6. 每次会话结束前，本次变更意图的新增、修改或删除必须写回 `draft.md`；尚未确认、存在歧义或冻结状态不允许写回时，必须输出修订建议，清楚说明建议文本、原因和下一步。
7. 需求只能从 `draft.md` 派生；代码、规则和当前规格可以用于解析技术目标、校验、解释或识别冲突，但不得补全用户未表达的需求。

用户确认 `[AI 推断]` 后，AI 在同一轮将其改为普通条目；用户否决时删除该条目，不在正文保留讨论历史。

## SDD 执行上下文隔离

SDD 命令只以当前命令输入、命令定义允许读取的当前工作区文件和当轮按职责产生的真实工具结果作为业务依据；普通讨论不受本节限制。

- 历史聊天、推断、旧摘要和旧工具输出不是规范性输入，不得替代当前文件或当轮结果。
- 影响命令结果的业务信息必须先写入所属变更文档；未固化的信息不得驱动阶段执行。
- 每次执行命令都必须重新读取当前状态和命令规定的必要文件，不得用历史记忆替代。
- 当前消息新增、修改或删除变更意图时，必须先写回 `draft.md`；当前状态不允许写回时停止，并提示执行 `/sdd-revise`。
- 必要文件缺失或未固化的信息影响当前命令时，必须报告并按工作流处理，不得自行补全、直接采用或静默忽略后宣称完成。

## 需求来源与计划补齐

- AI 执行阶段命令时，必须重新读取当前 change 的 `draft.md`；以 frontmatter 判断阶段，以正文判断用户意图，并遵守本文件的 SDD 执行上下文隔离规则。
- 命令文件明确列出的固定上下文必须读取；标为“所需”“按需”或“仅为”的上下文只在对应事实未确定时读取。已完整读取且未变化的文件不得重复读取。
- 用户意图和产品需求只能从 `draft.md` 派生。当前规格、目标 API 或产物、适用规则、参考资料和正式代码只能约束或解析既定意图，不得增加用户未表达的功能、输入、输出、默认值、失败行为或验收边界。
- `/sdd-plan` 必须补齐技术目标、工程约束、直接依赖、处理顺序、类型与隔离边界、失败门禁、非目标、实施顺序和验证门禁。直接依赖的类型或错误边界无法由规格和规则确定时才读取实际调用链；指定文件违反规则时必须在 plan 中记录修正。
- 推导结果会新增或改变可观察行为、存在多个合法选择或无法唯一确定时，必须记录待确认问题；需要写回 draft 时标记 `[AI 推断]`，并保持 `draft` 状态。
- 可观察行为与失败边界写入 `plan/spec.md`；实现决策、依赖、调用位置、上下文、处理顺序、类型与隔离边界写入 `plan/design.md`；实施顺序和门禁写入 `plan/tasks.md`；非目标写入能约束该边界的 spec 或 design。
- 生成或刷新 plan 时必须逐条落实适用规则；遗漏、冲突、无法落实或仍待确认时不得进入 `planned`。

## draft.md 格式

模板 change 每次只包含一个主要命名模板；其他模板作为依赖或独立 change 处理。技术目标不是 draft 的必填项；用户如果已经知道目标，可以直接在正文写明。

```markdown
---
status: draft
change-id: <kebab-case>
---

# <变更名称>

> 用户唯一输入入口。
> 只需编辑下面的“目标、需求、约束、非目标、验收”。
> 如果在会话中说明修改内容，AI 必须将确认后的修改写回本文件。

## 目标

- <目标>
- 依赖 `<外部能力>`，不属于当前实现范围。

## 需求

- <输入、输出、默认值或失败行为>
- `[AI 推断]` <待确认的建议>

## 约束

<!-- 只填写用户明确指定的本次特殊限制；AI 建议必须保留 [AI 推断]。 -->

## 非目标

- <本次明确不处理的内容>

## 验收

- <可观察且可判定的结果>
```

- frontmatter 只包含 `status` 和 `change-id`；状态取值以 [`openspec/workflow.md`](../workflow.md) 为准。
- 条目不强制编号；需要引用时使用章节名加条目原文。
- “约束”允许为空。项目基线、通用规则、代码事实或历史决定不得作为普通条目写入；AI 建议只能标记为 `[AI 推断]`。
- 依赖只声明当前目标调用所需的边界；不展开未实现子模板的字段或任务。
- 初始 draft 保持轻量，不写方案比较、任务、验证记录或长篇背景。

## AI 产物

- `plan/spec.md` 始终创建，首节 `## 技术目标` 记录 `capability`、`artifact-type`、`template-name` 和 `target-path`。非模板产物的 `template-name` 标为“不适用”；尚未唯一确定的字段记录候选项和待确认问题，不写猜测值。
- `plan/design.md` 只记录真正影响实现的决策；`plan/tasks.md` 使用 Markdown 任务列表，只列 `/sdd-apply` 的简短实施顺序，不包含验证步骤。
- 三个 plan 文件首行都指向 `draft.md` 作为需求修改入口。

不得把 Git 历史、归档 change 或旧 design 当作当前约束。当前规格可用于识别现行契约与冲突，但不能覆盖本次 draft 的明确变更。

## 摘要与记录

批准记录保存人类可读的冻结范围，以及 `plan/spec.md` 和 `plan/design.md` 的存在性与普通 SHA-256；`plan/tasks.md` 不属于契约，不冻结。批准后只允许 `/sdd-apply` 更新其中既有任务的完成状态，不得改写任务内容或顺序。记录中的 `plan/spec.md` 和 `plan/design.md` 存在性与摘要全部匹配时，批准才有效；`plan/tasks.md` 的完成状态变化不影响批准有效性。摘要只用于完整性核对，不能代替用户主动执行 `/sdd-approve` 或真实验证证据。

draft 正文在 plan 生成后发生变化时必须重新执行 `/sdd-plan`。批准前由 `/sdd-approve` 审查 draft 与 plan 是否一致；批准后需求变化必须通过 `/sdd-revise` 重置状态并移除既有 `plan/` 与 `records/`，使下一次 `/sdd-plan` 只从保留的 draft 正文重新派生，不再为 draft 维护特殊摘要算法。

`records/verification.md` 只由 `/sdd-verify` 根据当前正式实现和当轮真实命令创建或覆盖，固定使用人类可读的 Markdown，不使用 YAML 保存证据：

```markdown
# 验证记录

## 验证范围

- change、冻结契约摘要、目标文件和直接依赖及其 SHA-256。摘要用于确认验证对象未变化，不代替命令证据。
- 总结论：通过或失败。

## 环境

- 实际工具及版本。
- 与结果相关的运行环境。

## 场景 `<名称>`

- 命令：仓库真实存在并在当轮实际执行的完整命令。
- 输入：测试值或 fixture。
- 退出码：实际退出码。
- 预期：冻结 Scenario 对应结果。
- 实际：stdout/stderr 的必要摘要。
- 结论：通过或失败。

## Fixtures 与限制

- 记录临时 fixture、隔离验证边界和未覆盖内容；没有时明确写“无”。
```

静态推断、预期描述、摘要值或旧命令结果不能形成通过结论。批准失效，或者验证范围内的正式实现或直接依赖发生变化时，既有验证记录失效，必须重新执行 `/sdd-verify`。
